# Backend Development Plan

## Project Status

This is currently an unnamed SEO SaaS product.

The final product name and `.com` domain have NOT been decided.

IMPORTANT:
- Do not hard-code a product/brand name into the backend.
- Do not name backend packages, database tables, services, or APIs after a temporary brand name.

# Product Vision

The product will eventually be a SaaS platform that helps businesses improve
their visibility across:

1. Traditional search engines
2. Reddit/community discussions
3. AI answer engines
4. Content/search opportunities
5. Technical SEO

The five existing frontend modules represent the eventual real product:

1. Technical SEO
2. Search Opportunities
3. Reddit Opportunities
4. AI Visibility
5. Content Generator

The current website demonstrates these capabilities using simulated data.

The backend will progressively replace those simulated results with real
data and real processing.

+------------+-------------+

The backend should use a layered architecture:

Controller
↓

↓

PHASE 1 — WEBSITE / TECHNICAL SEO FOUNDATION
Objective

Build the first genuinely working backend capability:

User/Frontend
↓
Create a Project from a website URL
↓
Start an SEO analysis
↓
Backend fetches/crawls the website
↓
Backend performs basic technical SEO checks
↓
Results are persisted in PostgreSQL
↓
Frontend/API can retrieve the analysis

We are NOT implementing all five product modules yet.

Initial Domain Model

Represents a website being analyzed.

Suggested fields:

id
name
website_url
domain
created_at
updated_at

Constraints:

website_url is required
website_url must be a valid HTTP/HTTPS URL
domain should be normalized
timestamps should be generated by the backend
CrawlRun

Represents one execution of a website analysis.

Suggested fields:

id
project_id
status
started_at
completed_at
pages_discovered
pages_crawled
error_message
created_at

Possible statuses:

PENDING
RUNNING
COMPLETED
FAILED

A project can have multiple crawl runs.

Do NOT overwrite the previous analysis every time.

CrawledPage

Phase 1.3 — API

Initial API should be small.

Create Project

POST /api/projects

Request:

{
"name": "My Website",
"websiteUrl": "https://example.com"
}

Response should contain:

project id
name
normalized URL/domain
timestamps
Get Project

GET /api/projects/:projectId

Returns project information.

Start Analysis

POST /api/projects/:projectId/crawls

Creates a crawl/analysis run.

The response should identify the crawl run.

Example:

{
"id": "...",
"projectId": "...",
"status": "PENDING"
}

Get Crawl

GET /api/crawls/:crawlId

Returns:

crawl status
progress/basic counters
timestamps
error if failed
Get Analysis Results

GET /api/crawls/:crawlId/results

Returns structured technical SEO results.

The response should include:

crawl summary
pages
issues
basic health information

Do not attempt to reproduce the entire frontend dashboard response yet.

Return clean backend/domain data.

Phase 1.4 — URL Validation

Before crawling:

Validate the URL.
Require HTTP or HTTPS.
Normalize the URL.
Extract the domain.
Reject obviously malformed URLs.
Prevent unsupported protocols.

The crawler must never blindly request arbitrary malformed input.

Phase 1.5 — Basic Crawler

Implement a simple controlled crawler.

Initial behavior:

Start from the project's website URL.
Fetch the page.
Parse HTML.
Extract internal links.
Normalize internal URLs.
Add undiscovered internal URLs to the crawl queue.
Continue until the configured page limit is reached.
Store each crawled page.
Record relevant HTTP/SEO information.

The crawler should initially have a conservative page limit.

Example:

MAX_PAGES = 50

Do not crawl an unlimited number of pages.

Crawler Safety Rules

The crawler must:

stay within the target domain
respect HTTP/HTTPS rules
have a maximum page limit
have a request timeout
avoid duplicate URLs
avoid infinite loops
avoid repeatedly fetching the same URL
handle HTTP errors
handle redirects
handle invalid HTML
handle connection failures
identify non-HTML resources and avoid treating them as pages

Do not build an aggressive crawler.

Phase 1.6 — robots.txt

Check:

/robots.txt

Store whether it exists.

Where practical, use robots.txt information to determine whether pages
should be crawled.

Do not claim that robots.txt controls every aspect of search engine
indexing.

For the initial implementation, keep the behavior conservative and
document the crawler's exact behavior.

Phase 1.7 — XML Sitemap

Check common sitemap locations.

At minimum:

/sitemap.xml

If a robots.txt file specifies a sitemap, consider that location too.

Record whether a sitemap was found.

If possible, use sitemap URLs as additional crawl seeds.

Do not assume every website has a sitemap.

Phase 1.8 — Technical SEO Checks

Initial checks should include:

HTTPS

Determine whether the supplied website uses HTTPS.

HTTP Status

Record HTTP status code for every fetched page.

Flag unexpected non-2xx responses where appropriate.

Title

Check whether an HTML page has a title.

Flag:

missing title

Do not initially attempt complex title-quality scoring.

Meta Description

Check whether a meta description exists.

Flag:

missing meta description

Do not initially score writing quality.

Canonical

Check for canonical URL.

Record:

canonical URL
whether it is missing

Do not initially attempt complicated canonical conflict detection.

Robots / Indexability

Inspect robots meta directives where present.

Record whether the page contains:

noindex
nofollow

Keep this separate from robots.txt rules.

Internal Links

Extract internal links.

Record broken internal links when a fetched internal URL returns an
appropriate failure status.

Do not crawl external domains.

Phase 1.9 — Health Score

The frontend currently displays an overall health score.

Do NOT blindly invent a score.

Create a documented, deterministic scoring method only after the underlying
checks exist.

The score should be derived from actual collected signals.

For example, conceptually:

Health Score
100

weighted penalties for verified technical issues

The exact scoring weights must be documented and kept in one place.

Do not scatter scoring logic across controllers.

Phase 1.10 — Error Handling

The backend must return consistent errors.

Examples:

400
Invalid website URL

404
Project not found

409
Conflict where appropriate

500
Unexpected server error

Crawler-specific failures should be represented in the crawl run status
rather than causing the entire API process to crash.

Phase 1.11 — Logging

Add basic structured logging for:

API requests
crawl start
crawl completion
crawl failure
important crawler errors

Do not log:

passwords
API keys
secrets
sensitive user data
Phase 1.12 — Environment Configuration

Secrets/configuration must come from environment variables.

Create:

.env.example

Never commit the actual .env file if it contains secrets.

At minimum, expect configuration for:

DATABASE_URL
API/server port
crawler limits
request timeout

Do not invent external API keys during Phase 1.

Phase 1.13 — Testing

At minimum, test:

Project creation with valid URL.
Project creation with invalid URL.
Fetching an existing project.
Starting a crawl.
Crawl completion.
Crawl failure handling.
Duplicate URL prevention.
Page limit enforcement.
Missing title detection.
Missing meta description detection.
Canonical detection.
Internal link handling.

Do not build a huge test suite yet.

Focus on the core behavior.

Phase 1.14 — Frontend Integration

Do NOT immediately rewrite the five frontend modules.

First prove the backend independently.

Use API requests to verify:

Phase 1 Definition of Done

Phase 1 is complete only when this flow works:

Backend starts successfully.
PostgreSQL connection works.
A project can be created with a website URL.
A crawl can be started.
The crawler discovers internal pages.
The crawler respects the configured limit.
Pages are persisted.
Technical SEO signals are persisted.
SEO issues are persisted.
Crawl status can be retrieved.
Results can be retrieved through the API.
Errors are handled cleanly.
No secrets are committed.
Existing Astro frontend still works.
Existing marketing/demo UI remains visually unchanged.
Development Philosophy

Build this as a real product, not a tutorial CRUD application.

Prefer:

clear domain models
small services
explicit responsibilities
validated input
deterministic behavior
testable business logic
provider abstraction
database integrity
useful error responses
maintainable code

Avoid:

premature microservices
unnecessary abstractions
giant controllers
business logic inside routes
hard-coded fake product data
hidden magic
unnecessary dependencies
building future features before the current phase works

When a future requirement is uncertain, keep the architecture extensible
without implementing speculative functionality.
